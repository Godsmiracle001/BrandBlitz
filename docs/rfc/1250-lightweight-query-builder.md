# RFC 1250: Introduce a lightweight query builder for apps/api/src/db/queries instead of raw pg strings

## Problem Statement

`apps/api/src/db/queries/` holds 20 files of hand-written SQL strings against the raw
`pg` `Pool` exposed by `apps/api/src/db/index.ts`'s `query<T>()` wrapper. There is one
shared helper, `apps/api/src/db/pagination.ts` (cursor encode/decode, `buildCursorWhere`
for compound keyset pagination), but no shared builder for the other patterns that
repeat across the 20 files — most visibly soft-delete filtering and dynamic `SET`/`WHERE`
clause assembly.

## Current State

### Soft-delete filtering: repeated by hand, 8 files

`grep -rl "deleted_at IS NULL" apps/api/src/db/queries/` matches 8 files. Representative
examples from `brands.ts` alone (5 occurrences in one file):

```typescript
"SELECT * FROM brands WHERE owner_user_id = $1 AND deleted_at IS NULL ORDER BY created_at DESC"
"SELECT * FROM brands WHERE id = $1 AND deleted_at IS NULL"
`UPDATE brands SET ${setClause} WHERE id = $1 AND owner_user_id = $2 AND deleted_at IS NULL RETURNING *`
```
Each file re-derives `AND deleted_at IS NULL` by hand; nothing enforces it's present on
every non-admin read, and one query in the same file (line 127) deliberately omits it
with an inline `/* include_deleted */` comment — a convention that only works if every
future author notices and follows it.

### Dynamic `SET`/`WHERE` assembly: hand-built per call site

`brands.ts`'s update query builds `setClause` as a manually-joined string of
`$n`-indexed fragments before interpolating it into the `UPDATE ... SET ${setClause}`
template — the kind of param-index bookkeeping a query builder removes entirely by
tracking placeholder indices itself.

### `pagination.ts`: the one existing precedent

Already generalizes cursor-based pagination (`encodeCursor`/`decodeCursor`,
`buildCursorWhere`, `buildCursorWhereSimple`, a shared `CursorQuerySchema` zod schema).
This is proof the team is willing to build shared query infrastructure when the
duplication is painful enough — soft-delete filtering and dynamic `SET` clauses are the
same shape of problem, just not yet generalized.

### Prior art: ADR 003 rejected ORM *migrations*, not query building

`docs/adr/003-migrations-framework.md` chose a hand-rolled SQL migration runner over
Drizzle/Kysely/Prisma **auto-migrations** — i.e. generating schema DDL from TypeScript
models. That's a different concern from this RFC: Kysely-as-query-builder only touches
how `SELECT`/`INSERT`/`UPDATE` statements against an *already-migrated* schema get
built and typed; it has no opinion on how the schema itself evolves, and doesn't
require adopting Kysely's own migration tooling. Kysely can point at the existing
hand-rolled-migrated schema via its `kysely-codegen` types generator without touching
`apps/api/scripts/migrate.ts` at all. ADR 003's reasoning doesn't block this proposal,
but the RFC should say so explicitly so a reviewer doesn't assume it re-litigates ADR
003 by another name.

## Proposed Solution

### Adopt Kysely, incrementally, for new/refactored queries only

Kysely is chosen over Drizzle/Prisma because it's a query builder, not an ORM — it
doesn't own the schema or impose a migration workflow, matching ADR 003's existing
hand-rolled-schema decision. It generates types from the live database
(`kysely-codegen`) rather than requiring a parallel schema-definition file to hand-sync
with the SQL migrations.

```typescript
// apps/api/src/db/kysely.ts
import { Kysely, PostgresDialect } from "kysely";
import { Pool } from "pg";
import type { DB } from "./kysely-types"; // generated by kysely-codegen from the live schema
import { config } from "../lib/config";

export const db = new Kysely<DB>({
  dialect: new PostgresDialect({
    pool: new Pool({ connectionString: config.DATABASE_URL, max: config.DB_POOL_MAX }),
  }),
});
```

A soft-delete-aware helper replaces the repeated `AND deleted_at IS NULL`:

```typescript
export function notDeleted<T extends { deleted_at: Date | null }>(
  qb: SelectQueryBuilder<DB, any, T>
) {
  return qb.where("deleted_at", "is", null);
}
```

Rewriting one representative query from `brands.ts`:

```typescript
// Before
await query<Brand>(
  "SELECT * FROM brands WHERE owner_user_id = $1 AND deleted_at IS NULL ORDER BY created_at DESC",
  [ownerId]
);

// After
await notDeleted(db.selectFrom("brands").selectAll().where("owner_user_id", "=", ownerId))
  .orderBy("created_at", "desc")
  .execute();
```

### Incremental adoption — no big-bang rewrite

- New queries in new files use Kysely from day one.
- Existing files are migrated function-by-function when they're touched for an
  unrelated reason (bug fix, new field), not in a dedicated rewrite sprint.
- `db/index.ts`'s raw `query<T>()` wrapper and the `pool` export stay exactly as they
  are — Kysely's `PostgresDialect` wraps its own `pg.Pool` (or can be pointed at the
  same `pool` export, see Open Questions), so nothing about the raw-SQL escape hatch
  goes away. Both styles coexist in the same file indefinitely if needed.
- `pagination.ts`'s cursor helpers are kept as-is short term; a follow-up (out of scope
  here) could migrate `buildCursorWhere` to Kysely's own `where` composition once
  enough call sites have moved.

### Explicitly out of scope

- **No change to escrow/payout SQL during initial rollout.** `db/queries/payouts.ts`,
  `refunds.ts`, `multisig.ts`, and anything touching financial state stays on raw `pg`
  strings until the incremental migration has proven itself elsewhere first — these are
  the highest-blast-radius queries in the codebase and the last place to introduce a
  new tool's learning curve.
- No change to `apps/api/scripts/migrate.ts` or the `migrations/` SQL files (ADR 003
  stands).

## Benefits

1. **Type-safe SQL** — column typos and type mismatches (e.g. passing a `string` where
   the column is `uuid`) become compile errors instead of runtime Postgres errors.
2. **Less duplicated pagination/filter logic** — `notDeleted()` and Kysely's own
   `where`/`set` builders remove the hand-indexed `$n` placeholder bookkeeping visible
   in `brands.ts`'s `setClause` construction today.
3. **No parallel schema-definition file** — `kysely-codegen` reads the live database,
   so the hand-rolled SQL migrations stay the single source of truth for schema shape;
   Kysely's types are generated, not hand-maintained.
4. **Escape hatch preserved** — Kysely supports raw `sql\`...\`` fragments for anything
   the builder can't express cleanly, so no query is blocked from adoption by an
   awkward edge case.

## Migration Plan

1. Add `kysely` + `kysely-codegen` as dependencies; wire a `db:codegen` script that
   regenerates `kysely-types.ts` from the dev database, run in CI to catch drift.
2. Add `apps/api/src/db/kysely.ts` and `notDeleted()` alongside the existing `db/
   index.ts` — no existing call sites change yet.
3. New queries (new files, or new functions in existing files) use Kysely going
   forward; this is a lint-guideline, not an enforced rule, for the initial rollout.
4. Opportunistically migrate existing non-financial query files when touched for other
   reasons — `brands.ts` is a reasonable first candidate given its existing duplication.
5. Revisit escrow/payout adoption in a separate, later RFC once the pattern has
   shipped safely elsewhere.

## Open Questions

1. Should Kysely's `PostgresDialect` share the exact same `pg.Pool` instance already
   exported from `db/index.ts` (avoiding a second connection pool against the same
   database), or run its own pool? Sharing is almost certainly right given
   `config.DB_POOL_MAX` already sizes the pool for expected concurrency — this needs
   confirming against Kysely's `PostgresDialect` API (`pool` accepts a pre-built
   `pg.Pool` instance directly, so this should be straightforward).
2. Does `kysely-codegen` run cleanly against this schema's use of `jsonb` columns
   (e.g. `fraud_flags.details`) and generate reasonable types for them, or does that
   need manual type overrides?
3. Who owns keeping `db:codegen`'s output committed and in sync — a CI check that fails
   the build on uncommitted diff, or manual discipline?
